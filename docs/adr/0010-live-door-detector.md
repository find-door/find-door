# ADR-0010: 별도 가상환경의 상주 문 검출기와 원본 RGB-D 묶음 발행

- **상태:** ✅ 결정 — 로컬 YOLOE 개발 연결
- **날짜:** 2026-11-03
- **관련 단계:** Find Door 실시간 통합

## 배경

기존 NanoDet는 문을 지원하지 않는다. 로컬 recon-report의 YOLOE 자산을 재사용하되
ROS Python 환경과 검출 환경을 분리하고 관측 시각을 유지해야 한다.
검출 완료가 원본 RGB-D 동기화 큐보다 늦으면 Detection2DArray만 발행하는 것으로는 입력을 조합할 수 없다.

## 선택지와 비교

| 방식 | 장점 | 제약 |
|---|---|---|
| 프레임마다 C CLI 프로세스 실행 | 기존 CLI 재사용 | 매번 모델 적재·프로세스 시작, 입력 지연 증가 |
| ROS 프로세스에 검출 의존성 직접 추가 | 간단한 함수 호출 | ROS와 외부 가상환경의 의존성 결합 |
| 별도 가상환경의 상주 worker | 환경 분리·모델 재사용 | IPC·프로세스 정리·원본 영상 보관 필요 |

## 결정과 이유

상주 worker는 기존 recon-report 가상환경에서 로컬 YOLOEDetector를 실행한다.
ROS 어댑터는 원본 RGB-D·CameraInfo 묶음을 보관하고, 단일 추론 작업과 최신 대기 묶음 하나만 유지한다.
완료 결과는 원본 영상 header·픽셀 좌표로 RGB/depth/CameraInfo/Detection2DArray를 함께 발행한다.
추론 완료 시각으로 관측 시각을 바꾸지 않는다.

worker IPC는 이미지 경로 요청과 JSON-lines 응답이며 ID·bbox·클래스·점수를 확인한다.
오류·시간 초과 뒤 worker를 정상 결과처럼 재사용하지 않는다.
종료는 생성한 worker 프로세스 그룹만 추적해 수행한다.

외부 설정·가중치·임베딩·소스를 변경하지 않는다.
실행 임시 설정에 자산 절대경로와 `release_policy=keep`을 명시하고 캐시도 임시 폴더에 둔다.
원본 설정 해시·정책 변경·실행 모델 해시를 상태에 보존한다. 가중치 설치·다운로드는 수행하지 않는다.

## 포기한 것 / 위험

외부 YOLOE Python 인터페이스와 임베딩 캐시 계약에 의존한다.
상주 정책으로 GPU 메모리를 유지하며 CPU·GPU 부하에 따라 입력 묶음을 교체한다.
완료 횟수는 신선한 문 지도 관측 성공 횟수와 다르다.
늦은 결과는 원본 시각으로 발행하고 mapper의 최대 지연·상태 TTL 정책으로 거부·unknown 처리한다.
YOLOv11 추가 학습 모델을 구현하거나 일반 실내 성능을 채택한 결정은 아니다.

## 검증 방법

[실시간 통합 진단](../door-live.md)에서 실제 Gazebo RGB-D·YOLOE·LiDAR SLAM을 함께 실행한다.
실제 map 발행자·scan·문 상태·저장과 프로세스 정리를 확인한다.
정지한 단일 문 모델의 개발 확인을 주행·상태 전이·독립 장소·실물 평가와 구분한다.
