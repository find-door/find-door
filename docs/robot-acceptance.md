# 실물 로봇 인수·검증 절차

이 문서는 실물이 도착했을 때 수행할 절차입니다. **실물 검증은 아직 수행하지 않았습니다.** 시뮬레이션·오프라인 검사 통과로 아래 항목을 완료 처리하지 않습니다. 담당자와 시험 장소를 정하고, 각 단계의 증거 파일·판정·날짜를 남깁니다.

## 1. 인수 기록과 정지 수단

- [ ] 플랫폼·LiDAR·RGB-D·IMU 모델, 일련번호, 펌웨어, 드라이버 버전 확인. [하드웨어 구성](hardware.md)의 `🔍`를 실제 자료로 채우기.
- [ ] OS, ROS, JetPack/L4T, 커널, 전원 모드와 드라이버 커밋 기록. [개발 환경](setup.md)의 개발 PC 값과 실물 값을 구분.
- [ ] 바퀴·케이블·센서 고정, 전원·배터리 상태, 이동 공간 확인.
- [ ] 현장 담당자가 물리 정지 수단과 복구 절차를 확인. 통신 단절·드라이버 종료 시 모터 정지 동작과 명령 watchdog 확인.
- [ ] 바퀴를 안전하게 띄우거나 이동을 제한한 상태에서 정지 기능부터 검사. 원격 `/cmd_vel` 0 발행을 물리 비상 정지의 대체로 취급하지 않기.

정지 동작을 확인하기 전에는 자율 주행을 시작하지 않습니다. 시뮬레이션용 `drive_route`를 실물에 그대로 실행하지 않습니다. 시험 중 이상이 생기면 현장 정지 → 원인 기록 → 정지 기능 재확인 순서로 진행합니다.

## 2. 토픽·시간·TF 계약

먼저 구동 명령 없이 센서 드라이버를 실행합니다. 실제 토픽을 아래 읽기 전용 명령으로 조사하고 [인터페이스 계약](interfaces.md)과의 차이를 기록합니다.

```bash
ros2 topic list -t
ros2 topic info --verbose /실제_토픽
ros2 topic hz /실제_토픽
ros2 topic echo --once /실제_토픽
```

- [ ] 센서별 토픽, `sensor_msgs/msg/LaserScan` 등의 타입, 주기·손실률·QoS, `frame_id`, 지연·타임스탬프 역행 여부 기록. 통과 범위는 실제 센서 사양과 요구사항으로 시험 전에 확정 (`🔍`).
- [ ] 실물 노드 `use_sim_time=false`; 여러 컴퓨터를 쓰면 시계 동기화 방식과 잔여 오차 측정. 드라이버의 장치 시각→호스트 시각 변환 확인.
- [ ] 실제 base 프레임과 센서 정적 TF를 측정값으로 정하고, 각 TF 발행자를 하나로 유지. REP 105 및 카메라 REP 103 광학축 확인.
- [ ] `odom → base` 발행자의 입력이 엔코더인지, IMU 융합인지 명시. slam_toolbox는 `/odom` 메시지가 아니라 TF를 사용하므로 센서 시각의 TF 조회 성공 확인.
- [ ] IMU 정지 바이어스·중력축·단위·공분산, 휠 회전 방향과 오도메트리 축·부호 확인. 위치·자세 변화가 없는 정지 시험부터 수행.

## 3. 카메라·외부 보정

- [ ] 실제 해상도에 대응하는 `CameraInfo`의 K/D/P 및 왜곡 모델, RGB와 depth의 프레임·정렬 여부 기록.
- [ ] depth 인코딩·단위·0/NaN/Inf·유효 거리 확인. RGB/depth 시간 차이와 허용 동기화 범위를 시험 전에 결정 (`🔍`).
- [ ] 자·표적 등 독립 기준으로 알려진 거리의 깊이 오차를 여러 거리에서 측정. RGB 픽셀과 depth 대응을 물체 경계에서 확인.
- [ ] base→카메라 광학 프레임 및 base→LiDAR 장착 변환 측정. 보정 파일, 방법, 날짜, 오차와 수정 이력 보관.
- [ ] 센서 메시지 시각의 TF로 투영한 점을 독립 표적의 위치와 비교. 최신 TF로 대체하거나 정답에 맞춰 보정을 임의 조정하지 않기.

## 4. 기록·재생과 저속 주행

- [ ] 정지 → 직진 → 회전 → 횡이동 순서로 현장 감독 아래 저속 시험. 각 구간 이동량을 독립 측정하고 메카넘 미끄러짐 영향을 기록.
- [ ] 실제 토픽 이름으로 LiDAR, IMU, odom, RGB, depth, 각 CameraInfo, `/tf`, `/tf_static` 기록 목록 작성. 실물에서는 시뮬레이션 `/clock`을 입력으로 사용하지 않기.
- [ ] 원본 rosbag을 저장소 밖에 보관하고 metadata, 토픽별 메시지 수·기간·타임스탬프·누락 확인. 이미지까지 기록할 때 저장 대역폭과 디스크 여유 측정.
- [ ] 로봇 구동 연결이 없는 별도 도메인에서 재생. 출력 지도·semantic 결과와 입력 센서를 분리하고 재생 시각·TF 중복 발행 여부 검사. 기록된 `/cmd_vel`을 실제 로봇으로 재생하지 않기.

기록마다 코드 커밋, 외부 드라이버 revision, 파라미터·보정 파일 및 SHA-256, 토픽 목록, 시험자, 장소·조명·장면, 시작/종료 시각, 제외 구간과 이유를 남깁니다. 이미지에 사람이 포함되면 연구과제의 보관·공유 범위를 확인하고 원자료를 커밋하지 않습니다.

## 5. 지도·객체 정확도와 성능 인수

- [ ] 시험 전에 합격 기준을 합의: 지도 거리/벽 위치 오차, 궤적 오차, 객체 위치 오차, 검출·오검출, 갱신 지연, 처리율, 최대 자원 사용량 (`🔍`). 기준을 결과를 본 뒤 변경하면 별도 실험으로 표시.
- [ ] 실측 벽·기준점과 SLAM 입력에 쓰지 않은 측정 장비/표적으로 정답 구성. 정답 측정 오차도 함께 기록.
- [ ] 지도와 정답 정렬은 명시한 강체 변환만 사용하고 축척을 맞추지 않기. 궤적 비교는 최초 정렬을 고정하고 중간 점프를 매번 재정렬하여 숨기지 않기.
- [ ] 반복 주행으로 변동과 실패 사례를 확인. 초기 비교는 같은 경로 3회 이상을 권장하며 최종 표본 수는 요구 신뢰도에 따라 확정 (`🔍`).
- [ ] 실제 대상 클래스·조명·가림·거리별 별도 평가셋 구성. 합성 색상 표적 검출 결과를 실제 객체 인식 정확도로 보고하지 않기.
- [ ] Jetson에서 CPU/GPU·메모리·온도·소비전력·추론 및 전체 지연·메시지 손실 측정. 전원 모드, 냉각, 모델·입력 크기, 측정 시간 기록. `tegrastats` 등 사용 가능 도구와 지속 운전 시간은 실물 확인 (`🔍`).
